`build.py` verifies exactly one pinned file: the manifest. A hand-edited `data/model/dim_team.csv` (or `game-eras.json`) does not fail the build — it succeeds, rewrites `public/data/`, and the new `meta.json` describes the drifted file. Verified: appending a well-formed edit to `dim_team.csv` then building prints `wrote 16 files` and `data:check` passes.

The upstream manifest cannot help: it lists curated entity exports and 280-odd payload digests, no model CSVs.

This is inside AGENTS.md rule 3's letter (only the manifest refusal is promised) and `data:check` does fail a hand-edit that was *not* rebuilt — but `data/PROVENANCE.md` says "if a pinned file is ever edited by hand, the artifact hashes change and `npm run data:check` fails", which stops being true the moment someone rebuilds. After that, only review of the committed diff notices.

Choose: have `refresh-data.sh` write per-file hashes into `pipeline/source.json` (it already hashes everything it writes) and have `build.py` verify them alongside the manifest; or state the boundary honestly in PROVENANCE and AGENTS so no one believes a stronger guarantee than exists. The first is more work and worth it if the pin is meant to be a proof.

Check: a hand-edited CSV in a scratch copy either fails the build or is documented as out of scope, and PROVENANCE's sentence matches whichever is true.

## Done — the stronger option

`pipeline/refresh-data.sh` now records `files` in `pipeline/source.json`: the
sha256 of all 20 pinned files, keyed by their path from the repository root and
sorted. The 14 model files and the 4 upstream tag files are hashed from the staged
pin; `champion-releases.json` and `team-shortnames.json` are hash-pinned by their
own fetch scripts, so they are hashed from the installed copies. The refresh
verifies the map against the staged tree and again against the installed tree, so
a refresh cannot install a pin whose record is already wrong.

`pipeline/build.py` verifies every recorded hash, and does it before DuckDB opens
a CSV: a missing or hand-edited model file is the pin's refusal, not a DuckDB
binder or IO error. That ordering was a second defect the scratch proof found —
`main()` connected first, so a malformed edit or a deleted CSV died with a
traceback instead of the message. The refusals:

| case | message |
|---|---|
| recorded file missing | `error: data/model/dim_team.csv is missing; run pipeline/refresh-data.sh` |
| recorded file changed | `error: data/model/dim_team.csv is not the file pipeline/source.json pins`, then `pinned:` and `on disk:` |
| file on disk unrecorded | `error: data/upstream/notes.md is not recorded in pipeline/source.json` (a refusal: `meta.json` already treats the directory as the rule) |
| pin records no map | `error: pipeline/source.json records no per-file hashes` |
| manifest changed or missing | unchanged from before |

`data/PROVENANCE.md` and `AGENTS.md` rule 3 now state exactly this, and the claim
that `data:check` catches a hand-edit forever is gone.

Verified. `npm run check` green (230 vitest, 10 pipeline tests, `data:check`
current, production build). Refreshing `v1.1.0` is a no-op apart from the new map
— a second run leaves `source.json` byte-identical, and `meta.json` is the only
artifact that changed. Two consecutive builds are byte-identical. On a scratch
copy at `/tmp`, appending a row to `data/model/dim_team.csv` refused with the file
and both hashes, every refused build left `public/data/` byte-identical, and
restoring the file built and checked clean. Mutation evidence: deleting
`verify_pin` fails 4 tests, deleting `verify_manifest` fails 2, both green at 10.
