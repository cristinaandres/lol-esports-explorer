When usePlayerGames or useGameDetail fails on the player, champion or team page, the page shows skeleton blocks forever: only the game page surfaces the error.

Three pages need the branch the game page already has, with a message and a retry.

Fixed in 8a1a3e8. `useAsync` now returns `retry` alongside the state (an
`AsyncState`), and calling it puts the state back to loading before bumping the
attempt the effect listens for; the fresh request comes from `memoised`, which
forgets a rejection as it passes through. The three pages share a new
`LoadFailure` component, which names the artifact, repeats the loader's message
and offers the retry. The player page names its games, the team page its rosters
(the two roster sections are replaced by one block rather than two cards) and the
champion page names the picks and the bans separately, because it can be missing
either. The loading half still uses the shared `Skeleton`.

Verified with `npm run check` and on the built site over CDP, using
`Fetch.failRequest` on `player-games.json` for the player and team pages and on
`bans.json` for the champion page. The rendered failures were "Could not load
this player's games.", "Could not load this team's rosters." and "Could not load
the bans."; no skeleton remained on any of them, and allowing the request and
clicking Try again recovered each page to its real content. The game page still
loads normally, and forcing `sides.json` still prints its existing "Could not
load the game detail" line with no retry.
