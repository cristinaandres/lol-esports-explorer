The short-name guard has a blind spot and no test.

**Blind spot** (`pipeline/sql/08_shortnames.sql`): `shortname_matches` partitions by `t.team_id` and `ambiguous_shortnames` counts `distinct t.team_id`. `dim_team`'s real key is `team_key`. A second `team_key` under the same `team_id` was added in a scratch copy: `ambiguous_shortnames` stayed **empty**, `team_rank = 2` was silently assigned, the build succeeded, and that team's `teams.json` row lost its short name — exactly the silent drop the guard exists to refuse. `team_id IS NULL` rows fold into one partition the same way.

**No test**: deleting `report_shortname_defects` from `main()` leaves the pytest suite at **5 passed**. The four `render()` refusals are mutation-covered; this fifth one, which runs in `main()` and therefore on both paths, is not.

Fix: key the guard on `(team_id is not null, team_id, team_key)` or refuse a null id in the join, and add a test — either a stubbed connection returning one `unmatched_shortnames` row, or a small real-DuckDB integration case — that fails when the call in `main()` is removed.

Check: a duplicated `team_key` under one `team_id` fails the build with the ambiguity message, and removing the `report_shortname_defects` call turns the suite red.
