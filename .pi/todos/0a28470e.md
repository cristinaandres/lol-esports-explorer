The short-name guard had a blind spot and no test.

**Blind spot** (`pipeline/sql/08_shortnames.sql`): `shortname_matches` partitioned by `t.team_id` and `ambiguous_shortnames` counted `distinct t.team_id`. `dim_team`'s real key is `team_key`. A second `team_key` under the same `team_id` was added in a scratch copy: `ambiguous_shortnames` stayed **empty**, `team_rank = 2` was silently assigned, the build succeeded, and that team's `teams.json` row lost its short name — exactly the silent drop the guard exists to refuse. `team_id IS NULL` rows fold into one partition the same way.

**No test**: deleting `report_shortname_defects` from `main()` left the pytest suite green. The four `render()` refusals were mutation-covered; this fifth one, which runs in `main()` and therefore on both paths, was not.

**Changed.** Both halves of the guard are keyed on `team_key` now: the rank partitions
by it and `ambiguous_shortnames` counts `distinct t.team_key`. It is the row's primary
key, never null, and the key `team_short_name`, `team_index` and `teams.json` already
join on, while `team_id` is only the natural key the DDL declares UNIQUE — and the build
reads a CSV, not the DDL, so nothing enforced it. Each row now ranks on its own, so a
second row under one id cannot take another's short name, and two rows sharing an id
(including two null ids) are two teams in `ambiguous_shortnames`, which `main()` refuses.
The report's closing line names that second cause as well, because "the fold is too
coarse" was the only explanation a reader was given for two identical team names.

**Tested.** `pipeline/tests/test_build.py` gains six tests over four cases: a stub
answering the two defect views covers `main()`'s call for both the unmatched and the
ambiguous row (`status == 1`, the message, and no artifact written), and a control that an
empty defect set still writes `teams.json`; a two-row `dim_team` and a one-row pin in a
temporary directory run the real `08_shortnames.sql` against real DuckDB for the
duplicated id and the null id, plus a control that one name reaching one team stays quiet.
No model copy: the file reads its two inputs by relative path, so a temporary directory
holding a `dim_team.csv` of two rows and a pinned short name is enough.

**Verified.** Mutation evidence, each reverted before the commit: keying the SQL back on
`team_id` (both the partition and the two counts) failed both parametrised integration
cases with `ambiguous_shortnames` empty, the state the review found; deleting
`report_shortname_defects(con)` from `main()` failed the two `main()` cases — the old gap,
now red. In a scratch copy of the tree at the previous commit, a second `team_key` 9999
under `team_id tm-017ed54b4572` with the CSV hash re-pinned made the old build exit 0 and
write `{"team_key":9999,...,"short_name":null}` while the ambiguity view stayed empty; the
same tree with the fixed SQL exits 1, printing `error: pinned short name 'MAD' for 'MAD
Team' folds onto more than one team: MAD Team | MAD Team`. `npm run check` green: 232
vitest tests, 16 pipeline tests, `public/data is current (16 files)`, production build.
`teams.json` and every other artifact are byte-identical, as the pin carries no duplicate
key.
