src/lib/data.ts memoises each artifact in a module-level promise. If a fetch fails once, the rejected promise is kept for the session: every later navigation replays the same failure with no retry short of a reload.

Clear the slot before rethrowing, so the next navigation tries again.

## What changed

`src/lib/data.ts`. The module-level `let eager / playerRows / selectionRows /
aliasRows / detail: Promise<T> | null` slots are replaced by `memoised(load)`,
a small helper that remembers the attempt only once it succeeds. The catch on
that attempt empties the slot and rethrows, so the next caller starts a fresh
request; the promise in flight is still the one every earlier caller holds, so
nothing is served from a half-cleared cache.

All five loaders go through it:

- `loadDataset()` — the eager set of ten files, which the ticket also named
  even though it is not in the lazy set.
- `loadPlayerGames()`, `loadSelection()`, `loadAliases()` — one artifact each.
- `loadGameDetail()` — the composed loader. It clears its own slot, and the
  player rows it calls clear theirs, so a detail that failed on the scoreboards
  does not leave the shared row slot stuck on a rejection.

The module comment claimed the artifacts were "kept for the session"; it now
states the contract that actually holds — fetched once, once it succeeds — and
the doc block on `loader.test.ts` says the same. No behaviour changed for a
successful load: the exported functions, their signatures and the hooks are
untouched.

## What was verified

`npm run check` passes: lint, 200 vitest tests, `data:check` (artifacts
current), and the production build.

Four tests in `src/lib/loader.test.ts`, in a new `retrying a failed load`
block, using the file's existing seam (a fresh module per test via
`vi.resetModules()`, `fetch` stubbed with `vi.stubGlobal`) plus a new helper,
`stubFetchRefusingOnce(file, payload)`, that refuses the first request for one
file and answers the rest:

- **asks again for the alias bridge after a refusal, and keeps the answer** —
  the first `loadAliases()` rejects with the `HTTP 503` message it was given,
  the second resolves, the third is served from the cache; exactly two
  requests, so the failure was not remembered and the success was.
- **asks again for the whole game detail, scoreboards included** — the first
  `loadGameDetail()` rejects, the second returns all four arrays and the third
  is cached. `sides.json`, `bans.json` and `picks.json` are requested twice
  each while `player-games.json` stays at one, which is the per-artifact cache
  still working inside the retry.
- **asks again for the player rows inside a game detail, not only the detail** —
  the refusal is on `player-games.json`, so the detail rejects; the rows then
  resolve on their own ask, the detail resolves, and the file was requested
  twice. Proves the nested slot forgets its rejection too, rather than the
  detail retrying and hitting the same stale rejection.
- **asks again for the eager set when the first page load was refused** —
  `loadDataset()` rejects on `eras.json`, the second call resolves, and the
  file was requested twice out of the attempt's ten files.

All four fail against the previous implementation (`git show HEAD~1:src/lib/data.ts`
restored temporarily), each replaying the cached refusal, so they are tests
that can go red.

## For a reviewer

- The only ordering that matters in `memoised` is that the slot is cleared
  *before* the rejection reaches the caller, so a caller that retries on
  failure never races an uncleared slot. Their test cover is the alias and
  player-rows cases.
- `TODO-8e2e76a8` (lazy-artifact error states in the routes) is the reason the
  route components were left alone; nothing in this change touches them.
- Unrelated, noticed while reading: `src/components/SearchBox.tsx` calls
  `loadAliases().then(...)` with no rejection handler, so a failed alias fetch
  surfaces as an unhandled rejection there rather than as a message. It now
  retries correctly, but it has no error state of its own.
